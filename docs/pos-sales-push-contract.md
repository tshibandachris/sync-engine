# POS sales push contract

## Request

Send sales as `changes.sales`, in client outbox order. Each item is one atomic unit:

- `sale`: represented by the sale fields at the item root (including client-generated UUID `id`)
- `lines`: immutable `sale_lines` rows, each with a client-generated UUID
- `stock_movements`: immutable inventory ledger rows, each with a client-generated UUID

The implementation currently accepts the item fields at the root together with `lines` and `stock_movements`. UUIDs are generated by the client.

Push dependencies in this order: **staff → products → cash_sessions → sales**. If a sale references a session that has not reached the server yet, it returns `invalid` with `cash session not found`; retry it after the session sync succeeds.

## Response

`results` always has exactly as many entries as `changes.sales`, in the same order. Each entry has all three keys:

```json
{ "id": "client-sale-uuid", "status": "applied", "reason": null }
```

Allowed statuses: `applied`, `idempotent`, `conflict`, `invalid`. `reason` is a string for `conflict` and `invalid`, and `null` for successful results. The client should correlate results by array position and sale UUID.

Each sale is inserted in its own database transaction. If one item fails validation or persistence, only that sale rolls back; later items continue. Same UUID plus same full sale/line/movement content returns `idempotent`; same UUID with different content returns `conflict` and preserves the stored sale.

## Voids and stock

A void is a separate immutable sale in the session where the void is performed. Its total, cash amount, mobile amount, and line quantities must be the exact negatives of the original sale's values; each line must retain the original product ID. Otherwise the result is `invalid` with `void amounts do not mirror original sale`. A second void of the same original is a conflict.

Sale lines carry negative quantities for voids. Stock movements use the inventory ledger convention in migration 023: sale movements reduce stock (negative delta), while void movements restore stock (positive delta).

## Reconciliation

Sales are committed before derived reconciliation. After processing the batch, only sessions from sales with status `applied` are collected, and each distinct session is considered once. `idempotent` retries do not trigger reconciliation. Closed sessions are reconciled in separate transactions. Reconciliation sums **all signed** `cash_amount` values for the session, without filtering `is_void`, and writes only reconciliation-specific columns. Historical `closing_amount`, `expected_amount`, and `difference` are never rewritten. A reconciliation failure does not roll back sales.

## Tenant isolation for voids

Migration 021 enforces the composite foreign key `(tenant_id, voided_sale_id) REFERENCES sales(tenant_id, id)`, backed by the unique key `(tenant_id, id)`. The original-sale lookup is also scoped to the authenticated tenant. A cross-tenant void is rejected and cannot be inserted.

## Follow-up reconciliation job contract (out of scope for this PR)

The periodic reconciliation job belongs in its own branch and PR. Its candidate query is:

```sql
SELECT id
FROM cash_sessions
WHERE status = 'closed'
  AND reconciled_at IS NULL
  AND closed_at < (extract(epoch FROM now() - interval '24 hours') * 1000)::bigint;
```

For each candidate, the job calls the same reconciliation routine. It must distinguish a session with no sales rows from a session whose signed `SUM(cash_amount)` is zero because sales and voids cancel each other. If no sales rows have arrived after the 24-hour threshold, set `reconciliation_alert = true` and `reconciliation_alert_reason = 'no_sales_received'`. A zero signed sum alone is not sufficient evidence for that alert. The job must define retry cadence and repeated-failure behavior in its own reviewed contract; this PR does not add a scheduler or cron task.
